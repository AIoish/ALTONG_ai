# 긴급도·관련도 분리 실험

## 출발점

기준 브랜치: feature/filtering-score-separation. 원격 develop의 PR #16 병합
커밋 43aaef1에서 시작한다. 기존 v3 자료와 어댑터를 덮어쓰지 않는다.
기존 0.6B 파일럿은 검증 17/24, 긴급 알림 오차단 4/6이었다.
원문 8개 규모의 검증 결과이며 일반 성능으로 해석하지 않는다.

모델은 Qwen/Qwen3-0.6B, 정책은 urgency4_or_relevance4_v2로 고정한다.
긴급도는 알림 자체로 결정하고, 관련도는 현재 목적에 주는 도움으로 결정한다.
빈 창에서 쉬는 상태나 현재 작업을 추측하지 않는다.

## 비교군

| 군 | 입력 | 모델 목표 출력 | 목적 |
| --- | --- | --- | --- |
| A 전체 | 알림 + 문맥 | 기존 네 필드 JSON | 현재 방식의 재현 |
| B 점수 | 알림 + 문맥 | urgency_score, relevance_score 두 정수의 JSON | A와 비교해 카테고리·설명 생성 부담 확인 |
| C 분리 | 긴급도: 알림만 / 관련도: 알림 + 문맥 | 각각 urgency_score 또는 relevance_score 하나의 JSON | B와 비교해 문맥 차단과 작업 분리의 효과 확인 |

C는 동일 기반 모델에 긴급도용·관련도용 별도 LoRA 어댑터를 둔다.
두 작업의 가중치는 공유하지 않는다. 추론 시 기반 모델을 한 번 로드하고
어댑터를 순차 전환한다. 각 어댑터 크기와 전환 비용을 기록한다.
이는 입력 차단뿐 아니라 작업별 학습도 바꾸는 비교이므로 효과를
입력 차단 하나만의 결과라고 해석하지 않는다.

긴급도 입력에서는 알림 ID도 제외한다. 기존 변형 ID의 related/unrelated/empty
접미사가 문맥을 드러내기 때문이다. 같은 원문의 알림 내용과 시각만 유지한다.

B·C는 오프라인 점수 실험이다. 카테고리·설명을 임의로 채워 기존
FilterLabel 파서를 통과시키지 않는다. 별도 엄격한 점수 검증과 평가를 사용한다.
각 출력은 정확한 필드, 1~5 정수만 허용하며 bool과 추가 필드를 거부한다.
PASS/BLOCK은 모델 목표에 넣지 않고 기존 정책 함수로 계산한다.
앱 적용에는 기존 네 필드 계약을 충족하는 별도 설계와 검증이 필요하다.

첫 보강 검수는 원문 8개 × 관련·무관·빈 창 3문맥, 24행이다.
후보는 outputs/v3_score_separation_01/review_batch_01.md에 기록한다.
검수 전에는 합성 후보로만 취급한다. 기존 42개 미검수 원문을 승인된
원문으로 승격하지 않으며, 기존 검수 범위도 그대로 기록한다.

2026-10-03 사용자 발언 `ㅇㅇ 이대로 진행해보자.`로 첫 묶음 점수와 문맥을 승인했다.
냉각 장치 고장은 기존 보류 원문 v3_21의 장비 장애 계열, 미확인 카드 승인은
v3_36의 요청하지 않은 승인 계열로 보수적으로 연결했다. 이는 작성자의
그룹 판단이며 자동 유사성 검증 결과가 아니다. 공유 창으로 후보 8개가 모두
연결돼 전체 묶음을 학습에서 제외했다. 승인된 후보와 제외 근거는 보존한다.
이번 비교는 기존 150건으로 진행하며 추가 데이터 효과를 포함하지 않는다.
다음 보강 묶음은 보류 그룹과 연결되지 않는 독립 창·원문으로 다시 검수한다.

검수 후 기존 학습 분할과의 그룹 관계를 확인한다. 기존 검증·테스트와
같은 알림, 동일 정보 창 또는 지정 유사 시나리오 그룹인 후보는 보강 학습에서
제외하거나 다시 작성한다. 평가 오류 원문을 그대로 복사하지 않는다.
원문·문맥·정답을 확정한 뒤 동일 보강 학습 데이터로 A/B/C를 비교한다.
추가 사례는 개선 목적의 학습 후보이므로 새로운 독립 평가 근거로 세지 않는다.

C 긴급도 학습에는 동일 알림의 문맥 변형을 한 번만 넣는다.
긴급도 정답이 변형 간 다르면 준비를 중단하고 검수한다.
관련도 학습에는 모든 학습 문맥 변형을 유지한다.

## 실행 조건

각 군은 기존 파일럿 어댑터를 이어 학습하지 않고 동일 기반 모델에서 시작한다.
NF4 이중 양자화, BF16, LoRA r=8 / alpha=16 / dropout=0.05,
q_proj,v_proj, 학습률 0.0002, batch 1, 최대 길이 768, seed 42를 출발 조건으로 쓴다.
thinking 비활성화와 결정적 생성으로 통일한다. 토큰 초과는 잘라내지 않고 오류 처리한다.

우선 각 작업 1 epoch로 제한한다. 보강 확정 전 스텝 수를 고정하지 않는다.
예를 들어 기존 데이터만 쓰면 A/B는 각 150건, C는 긴급도 50건·관련도 150건이다.
C의 총 업데이트와 처리 토큰이 다르므로 동일 계산량 실험이라고 주장하지 않는다.
군별 행 수·스텝·처리 토큰·훈련 시간·생성 토큰 수를 기록한다.
첫 비교로 경향을 확인한 뒤에만 학습량을 조정한다.

전체 출력의 생성 한도는 기존 설정을 보존하고, 점수 출력은 64토큰을 시작값으로 쓴다.
긴급도와 관련도를 합쳐 C의 한 알림 처리 시간으로 계산한다.
출력 한도에 도달한 잘림은 유효 JSON으로 간주하지 않는다.
기존 평가의 prompt hash 동일 비교는 다른 프롬프트 군에 사용할 수 없으므로
신규 비교는 각 군의 프롬프트 해시를 따로 기록하고 원문·분할·정답 해시 일치를 확인한다.

## 평가와 선택

검증 24건만 평가하며 최종 테스트를 모델 선택에 사용하지 않는다.
동일 알림 3문맥을 원문별로 묶어 아래 지표를 함께 기록한다.

- 유효 출력 비율, 긴급 사례 중 무효 출력 수, PASS/BLOCK 정답 수.
- 긴급 알림 오차단 수와 긴급 사례 실패 수(명시적 BLOCK + 무효 출력).
- gold BLOCK의 오통과 수. 무효 출력을 BLOCK으로 치환하지 않는다.
- 두 점수의 정확 일치, ±1 정확도, 유효 출력에서의 MAE.
- 원문별 긴급도 변동 범위(max-min), 세 문맥 모두 같은 긴급도를 낸 원문 수.
- 무관·빈 창에서의 긴급 알림 실패, 주제 유사 사례의 관련도 과대평가.
- 로딩 시간 별도, 워밍업 별도, 토큰화·생성·파싱·어댑터 전환을 포함한 알림별 처리 시간.
- 전체 처리 시간 평균·p95, 최대 GPU 메모리, 어댑터 저장 크기.

C가 문맥 없이 같은 긴급도를 내는 것은 구조상 보장되는 성질이지 정확도 증거가 아니다.
긴급도 정답과 오차단도 개선되는지 확인해야 한다.
A만 카테고리·설명 품질을 별도 평가하고 B/C와 그 지표를 비교하지 않는다.
긴급 실패 감소를 우선하되 오통과·전체 정답·지연의 악화를 함께 판단한다.
단일 seed·원문 8개 검증으로 최종 채택하지 않는다. 방향 선택 후 새로운
독립 검수 평가 자료를 준비하고, 최종 선택이 고정된 뒤 남겨 둔 테스트를 한 번 평가한다.

## 실행 명령

프로젝트 루트에서 가상환경 Python으로 실행한다. 준비 결과·실행 폴더가
이미 존재하면 덮어쓰지 않고 중단한다. 새 실행에는 새 폴더 이름을 사용한다.

```powershell
python -m filtering_training.preparation.prepare_score_experiment --approval-text "ㅇㅇ 이대로 진행해보자." --approval-date 2026-10-03
python -m unittest filtering_training.checks.test_score_separation -v
python -m filtering_training.modeling.run_score_pilot --prepared-root filtering_training/outputs/v3_score_separation_01/prepared --run-dir filtering_training/outputs/runs/2026-10-03-qwen06-score-pilot-01
```

처음 준비에는 승인 원본 review_batch_01.md가 필요하다. 승인을 새로 꾸며
재생성하지 않는다. 준비된 각 작업의 manifest와 SFT 해시를 학습 전에 확인한다.
학습은 기존 modeling/train.py의 함수만 재사용하며 기존 파일을 수정하지 않는다.
실행기는 오프라인 캐시의 0.6B 모델을 사용하고 작업별 독립 프로세스로 GPU를 순차 사용한다.

별도 재로딩 점검은 train_score_task의 --smoke로 각 2스텝 학습한 후,
evaluate_score_experiment의 --variant C --max-samples 3으로 확인한다.
이 점검은 성능 비교가 아니며, 본 비교는 네 작업을 새로 각 1회 학습한다.
비교기는 A/B/C 보고서의 같은 검증 ID·원문·정답·분할 해시를 확인하고,
원시 응답으로부터 점수를 다시 파싱해 보고서 지표를 재계산한다.
원래의 전체 출력 평가기는 그대로 유지한다.

## 파일 재사용과 실행기 통합 — 2026-10-04

사용자 지침: 기존 파일을 확장해서 처리할 수 있으면 새 파일을 만들지 않는다.
실험 조건은 옵션으로 구분하고, 같은 역할의 실행·비교·검증 코드를 재사용한다.
서로 다른 학습 목표나 생성 추론·직접 분류처럼 구현 역할이 다른 코드는 유지한다.
데이터·검수·승인·가중치·실험 결과는 출처와 비교 근거이므로 합치거나 덮어쓰지 않는다.
학습·평가 기록은 계속 기존 `docs/filtering-experiment-log.md` 아래에 추가한다.

실행 스크립트 네 개를 `modeling/run_score_pilot.py` 하나로 통합했다.
`--experiment`의 `pilot`, `controls`, `digit`, `supplement`, `threshold`, `fit`, `epochs3`으로 종류를 선택한다.
새 결과 경로는 `--run-dir`로 명시한다. `--dry-run`은 실행 명령만 보여 주며
파일 생성·데이터 준비·모델 로딩·학습을 하지 않는다.

숫자 비교 스크립트 두 개는 `modeling/compare_digit_scores.py` 하나로 통합했다.
`--experiment digit|supplement|threshold`와 `--runs`로 대상을 지정한다.
`--check-only`는 기존 비교 결과를 다시 검증하며 결과 파일을 변경하지 않는다.
보조 목표 실험에서 기존 관련도 어댑터 경로는 실행기·비교기의 `--baseline`으로 지정한다.

```powershell
python -m filtering_training.modeling.run_score_pilot --experiment threshold --run-dir filtering_training/outputs/runs/<새-실행-폴더> --dry-run
python -m filtering_training.modeling.compare_digit_scores --experiment threshold --runs filtering_training/outputs/runs/2026-10-04-qwen06-digit-threshold-01 --check-only
```

기능 통합 후 중복 파일 `run_score_controls.py`, `run_digit_scores.py`,
`run_digit_supplement.py`, `compare_digit_supplement.py`를 제거했다.
이전 실행 기록의 경로 문자열은 당시 이력이다. 재실행에는 위 통합 모듈을 사용한다.
학습·검증·진단 단계와 기존 결과는 유지하고 중복 프로세스 실행 및 예측 검증만 합쳤다.
통합 후 필터링 테스트 59개가 통과했고 숫자 분류·보강·보조 목표 세 실험의
비교 결과를 다시 계산해 저장된 결과와 동일함을 확인했다. 재학습은 하지 않았다.

최근 창 입력이 있는 오프라인 실험에서는 아래 기준을 적용한다. 기존 학습의 입력·프롬프트와 승인 자료는 당시 버전으로 보존한다.
