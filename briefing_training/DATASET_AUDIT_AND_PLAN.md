# 브리핑 데이터셋 점검과 개선 계획

기준: 로컬 `category_briefing_v9` 학습·검증 데이터 및 `independent_chat_evaluation.jsonl`. 숫자는 파일을 직접 읽어 센 결과이며, 테스트셋의 실제 대화 대표성이나 모델 성능을 보증하지 않는다. 2026-11-07.

## 현재 확인된 내용

- v9 학습 1,376건, 검증 200건. 각 행은 알림 묶음 하나를 나타낸다.
- 학습 묶음의 알림 수: 1개 52건, 2개 568건, 3개 88건, 4개 648건, 5개 10건, 7개 10건. **8개 이상은 없다.** 다만 메시지 개수만으로 멀티턴 자연스러움이나 실제 대화 적합성을 판단할 수 없다.
- 학습 1,376건과 검증 200건 모두 metadata의 `synthetic`이 true다. 기존 생성 코드에는 시나리오에 값을 끼우는 `template.body.format(**values)`와 표면 문구 추가가 있다. 데이터 전체의 작성 주체나 외부 모델/API 사용 이력까지 확정할 근거는 없다.
- 공백을 정리한 알림 본문 전체를 묶음 순서대로 이어서 비교할 때 학습 내 정확한 본문 중복 0건, 검증 내 0건, 학습·검증 간 정확히 일치한 본문 0건이다. **문구가 똑같지 않다는 뜻이지, 서로 다른 대화 구조라는 뜻은 아니다.**
- 학습과 검증의 metadata 시나리오는 각각 55종이며 55종을 공유한다. 검증 200건 모두 학습에도 존재하는 시나리오에 해당한다. 이 값은 메타데이터 기준으로, 서로 다른 시나리오 간 유사도를 측정하지 않는다.
- 각 검증 사례에서 **동일 시나리오** 학습 사례 중 본문 문자열의 `difflib.SequenceMatcher` 문자 유사도가 가장 높은 것을 찾았다. 200건 중 117건이 0.8 이상, 중앙값은 0.815였다. 이는 형태가 비슷하다는 참고치이며 의미 중복률이나 객관적 과적합 판정이 아니다. 시나리오 라벨 및 길이에 영향을 받는다.
- 현재 8건 평가 데이터는 6개짜리 1건과 7개짜리 7건인 합성 사례다. 같은 8건에서 기존 1.7B와 카톡 초안 50건 추가 학습 모델을 비교하면 JSON 통과는 6→7건, 전체 자동 조건 통과는 5→4건이었다. 사례가 적고 자동 검사가 의미 오류를 모두 잡지 못하므로 어느 모델이 전반적으로 우수하다고 단정할 수 없다.
- 추가 학습된 초안 50건은 10가지 템플릿을 다섯 번씩 바꾼 사례다. 7~15개 알림으로 구성했으나 단어 단위로 인위적으로 나눈 예가 있다. 새로 만든 길이 비교용 50건 역시 5개 유형에 짧은·장문 변형을 만든 합성 자료이므로 독립적인 실제 대화 50건이 아니다.

### 실제로 확인된 유사 예

학습 `service_recovery`:
> 가상 운영팀 안내입니다. 검색 서비스에서 오류가 발생했습니다. / 조치가 완료되어 검색 서비스가 정상화되었습니다.

검증 `service_recovery`:
> 새로운 안내입니다. 알림 서비스에서 오류가 발생했습니다. / 조치가 완료되어 알림 서비스가 정상화되었습니다.

시스템 이름과 첫 안내는 다르지만 핵심 문장 구조가 같다. 이 한 쌍이 모든 사례를 대표한다는 뜻은 아니다.

## 우선순위와 데이터 작업

1. **추가 학습을 멈추고 기준선을 고정한다.** 기존 1.7B 어댑터, chat50 어댑터, 실제 사용한 GGUF를 구분하고 평가 방법과 입력 프롬프트·생성 설정을 함께 기록한다. Python 어댑터와 GGUF의 결과를 같은 모델 수치로 혼동하지 않는다.
2. **독립 평가용부터 만든다.** 동의와 이용 권한이 확인된 실제 알림을 개인정보 제거 후 활용하거나, 직접 작성한 현실적인 가상 대화를 사용한다. 공개 데이터는 출처·라이선스·재배포 가능 여부를 기록한다. 상대방의 실제 대화는 익명화만으로 무조건 공개 가능하다고 가정하지 않는다.
3. **실패 유형을 먼저 명시한다.** 장소·시간 변경, 취소 후 재진행, 복구 완료와 미해결의 구분, 조건부·미확정, 여러 제출물과 마감, 잡담, 오타·축약·이모티콘, 여러 화자의 말, 관계없는 대화, 정보 부족 등을 다양하게 준비한다. 각 대화의 핵심 사실과 최종 상태를 사람이 확인하고, 과도한 추론 없이 기대 요약을 작성한다.
4. **입력 환경을 함께 구분한다.** 모델 단독 입력은 앱·발신자·방·메시지 순서가 실 서비스와 맞는지 기록한다. 실제 앱이 차단 알림만 입력하는 경우에는 전체 대화 입력과 차단분 입력을 별도로 시험한다. 다른 사람의 메시지가 중간에 빠진 경우도 평가한다. 지나치게 긴 묶음은 토큰 수와 잘림 여부를 기록한다.
5. **분할은 시나리오·대화 출처 단위로 먼저 한다.** 같은 대화, 표현만 바꾼 변형, 짧은/긴 버전과 같은 사건 계열이 학습과 평가에 동시에 들어가지 않도록 그룹을 정한 후 분리한다. 정확한 중복과 근접 중복은 별도로 점검하고 사람이 검토한다. 과거 공개된 테스트셋은 내부 회귀 점검용으로 유지하되 외부 모델의 미노출 테스트셋이라고 주장하지 않는다.
6. **사람 검토를 포함해 동일 조건으로 비교한다.** 입력 → 기대 요약 → 기존 모델 원본 → 변경 모델 원본을 사례별로 남긴다. JSON 형식과 카테고리 외에 사실 포함, 최신 상태, 취소·부정, 없는 내용 추가, 자연스러움을 별도로 기록한다. 각 척도의 판정 규칙과 검토자, 불일치 해소 방식도 기록한다.
7. **학습 여부는 평가 뒤 결정한다.** 파서·프롬프트·묶음 처리 문제와 모델 자체의 의미 왜곡을 구분하고, 필요한 경우에만 검토한 다양한 학습 사례를 기존 데이터와 적절히 섞는다. 학습 중 평가용을 수정하거나 학습에 넣지 않는다. 데이터 작성 시 모델이 생성한 정답은 원문과 대조해 사람이 승인해야 한다.

## 보류 중인 결정

- 실사용 데이터 사용 동의·익명화·공개 가능 범위 및 팀의 데이터 수집 방식.
- 클라이언트의 방 구분, 서로 다른 화자, 차단·통과 누락, 최대 묶음 길이 정책.
- 실제 서비스 목표(응답 시간, 메모리, 모델 입력 한도, 평가 통과 기준).
- 최종 학습 데이터 규모 및 수동 검토 예산. 숫자를 먼저 늘려 성능 향상을 가정하지 않는다.

기존 공개 자료의 특성과 한계는 데이터 카드에 계속 명시하며, 출처·라이선스 확정 전에는 실제 대화를 추가로 공개하지 않는다.
