# 브리핑 모델 데이터·학습·평가 및 연동 현황

기준: 로컬 작업 트리와 2026-11-06까지 보존된 실험 결과. 이 문서는 현재 확인한 사실과 미확인 항목을 구분한다. 기존 1.7B 모델과 추가 학습 시험 모델은 별개다. 실험 결과는 모델·실행 방식·데이터별로 비교해야 한다.

## 1. 데이터셋 구축 현황

`data/category_briefing_v9/`는 v8 데이터(학습 1,280 / 검증 176)에 보완 데이터(학습 96 / 검증 24)를 더한 **학습 1,376 / 검증 200건**이다. 생성 코드 `prepare_dataset.py`는 템플릿과 문자열 치환을 이용한 결정적 합성 데이터를 만들며, `prepare_category_dataset.py`가 분류·요약 사례를 구성한다. 사람이 쓴 템플릿인지, AI가 작성한 템플릿인지, 전체 자료에 GPT/Claude API가 사용됐는지 모든 계보는 확인되지 않았다. 확인 전 특정 출처로 단정하지 않는다.

카톡형 표현·분할 메시지·상태 변경 사례는 포함되나 실제 카카오톡 멀티턴 대화의 대표성이나 다양성은 검증하지 않았다. v9 학습 데이터는 알림 1개 52건, 2개 568건, 3개 88건, 4개 648건, 5개 10건, 7개 10건으로 7개 초과 묶음이 없다. 분류 라벨은 그룹 단위다.

추가 학습 시험은 별도 합성 초안 50건을 사용했다. AI 보조로 만든 10가지 템플릿 유형을 5개씩 변형했고 메시지 수는 7~15개다. 메타데이터에 검토 전이라는 표기가 남아 있으나 실제 학습에 사용되었다. 일부는 원문을 단어 단위로 나눈 인위적인 사례로 품질 검토가 필요하다. **v9와 50건 시험은 서로 다른 학습 실행이며 합계 1,426건으로 한 번에 학습한 것이 아니다.**

## 2. 학습 스펙과 손실

- 베이스: `Qwen/Qwen3-1.7B`; 모델 revision은 어댑터 설정에 기록되지 않아 확인되지 않음.
- 방식: QLoRA, 4비트 NF4 및 double quantization. GPU의 BF16 지원 여부에 따라 BF16 또는 FP16 연산. RTX 3050 Laptop GPU 4 GB 환경에서 수행한 기록이 있다.
- LoRA: r=16, alpha=32, dropout=0.05. 코드 설정 `target_modules=all-linear`; 실제 저장된 대상은 `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj`.
- v9: 3 epoch, batch 1, gradient accumulation 16, learning rate 1e-4, max length 2048. 기존 학습이 중단 후 재개된 이력이 있다.
- chat50 시험: v9 어댑터를 초기값으로 새 학습. 1 epoch, batch 1, accumulation 4, learning rate 1e-5, max length 2048; 기존 v9 검증 200건 사용. 새 optimizer/scheduler로 시작했다.

| 실행 | Train loss (기록값) | Validation loss 추이 |
|---|---|---|
| v9 | step 5: 1.0586 → step 85: 0.01017 → step 170: 0.000694 → step 255: 0.000689 | epoch 1: 0.04170 → epoch 2: 0.03336 → epoch 3: 0.03328 |
| chat50 시험 | step 5: 1.36987 → step 10: 1.29486; 종료 평균 1.32846 | epoch 1: 0.03297 |

v9 최종 `train_results.json`의 train_loss는 0.00020236이나 학습이 재개된 실행에서 기록된 집계값이므로 위 구간 loss와 직접 동등하게 비교하지 않는다. 검증 손실이 낮아졌다는 사실만으로 일반화나 과적합 유무를 단정할 수 없다. chat50은 1회 검증만 있어 추세를 판단할 수 없다.

## 3. 평가 데이터와 정량 결과

- v8 기본 평가 30건, 짧은 요청 8건, 별도 합성 대화 평가 8건이 존재한다. 각기 다른 목적의 파일이며 중복 가능성 검증 없이 합산하지 않는다. 평가 생성 코드와 학습 템플릿이 유사할 수 있어 **완전한 의미적 독립성은 보장되지 않는다.**
- 합성 대화 평가 8건은 chat50 추가 학습 50건에 넣지 않았다. 알림 ID를 제외한 모델 입력 전체를 대조했을 때 v9 학습·검증 데이터와 완전히 같은 입력은 각각 0건이다. 다만 유사 템플릿이나 의미적 중복까지 검증한 것은 아니므로 완전한 독립성은 보장하지 않는다.
- greedy 생성. 구조화 출력률은 JSON·필드·줄 수 등 검사 비율, 카테고리 정확도는 라벨 일치, 사실 포함률은 수동 정의된 문자열/동의 표현 포함 검사다. 사례 통과는 평가 코드의 조건 조합이며 사람 평가를 대체하지 않는다. ROUGE/BLEU는 이 결과에서 측정하지 않았다. 키워드 검사는 의미 역전이나 환각을 놓칠 수 있다.
- 1.7B v9, v8 기본 30건: JSON 형식 30/30, 카테고리 29/30, 전체 조건 23/30, 필수 사실 포함 92.59% (문자열 기반), 평균 138.30초/건. 실행은 Python Transformers 어댑터 추론이며 GGUF/앱 수치가 아니다.

| 합성 대화 8건 (동일 입력, Python Transformers greedy) | 기존 v9 | chat50 추가 학습 |
|---|---:|---:|
| JSON 형식 통과 | 6/8 | 7/8 |
| 원본 카테고리 정확도 | 6/8 | 5/8 |
| 교정 후 카테고리 정확도 | 5/8 | 5/8 |
| 전체 조건 통과 | 5/8 | 4/8 |
| 필수 사실 포함률 | 86.36% | 86.36% |
| 평균 응답 시간 | 248.03초 | 137.73초 |

두 실행의 시스템 부하가 같다고 확인되지 않아 시간 차이를 모델 성능 개선으로 해석할 수 없다. 평균은 기록된 wall time이며 샘플 수가 적다. 30건, 8건 지표는 항목 구성과 평가 조건이 달라 서로 직접 비교하지 않는다. 별도 짧은 15묶음/장문 15묶음 평가는 50건 추가 학습 사례와 유사 표현이 있어 독립 벤치마크로 보지 않는다.

## 4. GGUF 배포와 연동

- 기존 v9 1.7B의 Q8_0 GGUF 파일은 로컬에서 1,834,426,272 bytes (약 1.71 GiB)로 확인했다. **chat50 추가 학습 모델은 아직 GGUF로 변환·배포한 결과가 확인되지 않았다.** Q4_K_M은 별도 평가 후보이며 이 문서에서 새 모델로 배포됐다고 주장하지 않는다.
- 모델이 직접 생성하는 출력은 `{"primary_category":"일정/회의","summary_lines":["요약 문장"]}`이다. 최상위 두 필드만, 허용 카테고리, 1~3개 문자열, 각 줄 최대 160자. 세션·그룹·일정 추출을 합친 최종 UI 구조는 별도 앱 로직이다.
- Python 코드에서 생성한 정확한 시스템 메시지와 사용자 입력 예시는 [프롬프트 스냅샷](BRIEFING_PROMPT_SNAPSHOT.md), 구현은 [category_prompt.py](../src/briefing/category_prompt.py), 검사는 [qwen_prompt.py](../src/briefing/qwen_prompt.py)를 확인한다. 클라이언트 코드와 현재 Python의 완전 일치 여부는 버전별 확인이 필요하다.
- 위 8건 Python 평가 평균 248.03초/137.73초는 CPU offload 경고가 있었던 각각의 실행 기록이다. 이전 관측에서 Python 프로세스 peak working set 8,400.2 MiB는 특정 실행의 프로세스 전체 RAM이며 모델 단독·GGUF·항상 필요한 메모리를 뜻하지 않는다. GGUF의 모델별 peak RAM/VRAM과 동일 조건 단일 추론 속도는 **미측정**이다. RTX 3050의 4GB 전용 VRAM과 공유 메모리는 구분해야 한다.

## 5. 병목 및 다음 확인

1. 짧은 잡담을 여러 줄로 복사해 3줄 제한을 초과하거나 여러 JSON 객체를 출력한다. 파서 거부 시 클라이언트가 마지막 알림으로 대체할 수 있다.
2. 변경 전 장소 유지, 복구 완료 누락, 없는 내용 생성, 어색한 한국어 등 의미·문장 품질 문제. 8건에서 일부 개선과 악화가 함께 나타나 전체 개선은 확인되지 않았다.
3. OCR이 비텍스트로 수집한 알림과 모델 원본 출력 실패는 서로 다른 원인이며, 앱 최종 화면만으로 원인을 단정할 수 없다.
4. 긴 메시지 및 여러 묶음의 시간순 맥락 손실, 입력 토큰 길이·잘림 여부, 동일 클라이언트 입력에서의 재현성을 검증해야 한다.
5. 새 50건은 5개 유형의 변형으로 상대적으로 유사하며, 독립 테스트와 사람 검토·데이터 작성 이력 확인이 필요하다. 개인정보·저작권·라이선스 검토 전 공개하지 않는다.
