# KLUE 공동 학습: 긴급도 5단계·관련도 3단계

> 이 문서는 11월 3일의 기존 입력 계약 실행 기록이다. 11월 4일 코드부터는 기본 데이터가
> v13이며 `recent_processes`와 최근 창 목록의 현재 창 중복을 제외한다. 기존 실행 파일은 보존한다.
> 새 실행 방법은 [현재 학습 안내](filtering-windows-only-2026-11-04.md)를 따른다.

기존 모델처럼 공유 인코더 하나와 두 분류 헤드를 사용한다. 긴급도·관련도 모두 학습한다.
앞서 삭제한 관련도 전용 실험을 사용하지 않으며, 사용자가 중단한 새 5단계 대조군을 만들지 않는다.
기존 안전 보강 KLUE 5/5 모델과 비교한다.

## 통제 조건

기존 `2026-10-10-klue-base-02`와 `2026-10-10-base-safety-continue-01`의 실제 설정을 읽어 재사용한다.

| 항목 | 초기 학습 | 안전 보강 |
| --- | --- | --- |
| 학습 행 | 긴급도 4,946 / 관련도 10,173 | 긴급도 6,446 / 관련도 2,500 |
| 시드 | 42 | 73 |
| 최대 에폭 | 3, 기존 patience 2 | 2 |
| 인코더 학습률 | 2e-5 | 5e-6 |
| 헤드 학습률 | 1e-4 | 2e-5 |
| 유효/마이크로 배치 | 16 / 4 | 16 / 4 |
| 워밍업 | 10% | 5% |
| attention | eager | SDPA |

안전 보강 375행을 기존처럼 4회 반복한다. 관련도 재사용 2,500행은 기존 실행에 기록된 인덱스와
점수별 표본 추출 결과가 같은지 확인한 후 그대로 사용한다. 3단계로 합친 뒤 재추출하지 않는다.
전체 행·작업별 손실 비중·토크나이저·관측 입력·정규화 본문 기준 평가 분리를 유지한다.
최대 512토큰을 넘으면 조용히 자르지 않고 실패한다.

관련도 정답만 1→1, 2·3→2, 4·5→3으로 변환하고 관련도 출력 헤드를 3개로 바꾼다.
긴급도 정답은 바꾸지 않는다. 기존 두 5개 헤드의 초기 난수 소비를 재현한 뒤 관련도 헤드만
첫 3행으로 줄여, 긴급도 초기 가중치와 초기화 후 난수 상태가 기존과 같도록 한다.
안전 보강 시에도 기존처럼 모델을 재구성하고 초기 학습 체크포인트를 로딩한다.

선택 기준은 기존의 정책 정확도·긴급 누락·점수 정확도 및 안전 개발 평가 우선순위를 유지하며,
관련도 임계값만 4 이상에서 3점으로 바꾼다. 3단계 점수 정확도는 기존 점수의 동일 매핑 결과와 비교한다.
단일 시드의 과거 실행과 비교하므로, 부동소수점 연산 경로·선택 에폭의 차이가 존재할 수 있다.

## 평가와 보존

- 기존 검증 74행과 안전 개발 40행은 기존과 같이 체크포인트 선택에 사용한다.
- 기존 합성 진단 100행과 경계 진단 14행은 학습·선택에 사용하지 않는다.
- 합성 진단은 과거에 이미 평가한 AI 제안 자료이며 새로운 독립 최종 테스트는 아니다.
- 긴급도 점수·임계값 누락과 관련도 점수·누락·불필요한 통과를 분리해서 보고한다.
- 최종 모델의 ONNX와 GPU 점수 일치를 검사한다.
- 기존 데이터·모델 파일은 보호 해시로 유지하며 기존 앱과 C# 패키지는 수정하지 않는다.

```powershell
python -m filtering_training.modeling.joint_urgency5_relevance3 --run filtering_training/outputs/runs/2026-11-03-klue-joint-u5-r3-02 --dry-run
python -u -m filtering_training.modeling.joint_urgency5_relevance3 --run filtering_training/outputs/runs/2026-11-03-klue-joint-u5-r3-02
```

결과는 새 실행 폴더의 `initial/`와 `safety/`에 분리한다. 최종 모델은 `safety/model.pt`와
`safety/model-fp32.onnx`이며, 출력은 `urgency_logits [batch,5]`와 `relevance_logits [batch,3]`이다.
이 출력과 정책을 사용하려면 기존 C#의 단일 `[batch,2,5]` 출력 처리와 관련도 통과 조건을 조정해야 한다.

## 진행 상태

실행 01은 첫 에폭 완료 전에 중단했다. 기존의 stacked-head loss처럼 단일 과제 배치에서도
두 헤드의 기울기가 None이 아닌 0으로 전달돼 AdamW 감쇠가 유지되도록 맞춘 뒤 실행 02로 다시 시작한다.
관련 회귀 검사를 포함한 5개 핵심 테스트를 통과했다.


## 완료 결과

실행 02에서 초기 3에폭과 안전 보강 2에폭을 완료했다. 선택된 에폭은 초기 3·보강 1로 기존 모델과 같다.
긴급도와 관련도는 새 공유 인코더와 두 헤드에서 함께 학습·예측했다. 기존 긴급도 모델의 출력을 섞지 않는다.

| 평가 | 기존 전체 정책 정답 | 새 전체 정책 정답 | 기존 관련도 통과 정답 | 새 관련도 통과 정답 |
| --- | ---: | ---: | ---: | ---: |
| 검증 74행 | 68/74 | 65/74 | 72/74 | 68/74 |
| 안전 개발 40행 | 40/40 | 40/40 | 40/40 | 40/40 |
| 기존 합성 진단 100행 | 97/100 | 94/100 | 99/100 | 96/100 |
| 기존 경계 진단 14행 | 13/14 | 14/14 | 14/14 | 14/14 |

검증 74행에서 긴급도 점수 정답은 59→59, 긴급도 자체 임계값 누락은 3→3, 최종 긴급 차단은 2→2다.
관련도 누락은 1→1이지만 불필요한 통과가 1→5로 증가했다. 누락 사례의 ID는 서로 다르다.
기존 모델과 같은 학습·보강 절차로 두 점수를 공동 학습해도 이번 실행에서는 관련도 3단계의 개선을 확인하지 못했다.
새 모델은 보존하되 기존 앱 모델을 자동 교체하지 않는다. 단일 시드·작은 기존 평가의 결과이며 일반적인 열등함을 증명하지 않는다.

ONNX 출력은 긴급도 `[batch,5]`, 관련도 `[batch,3]`이며 228행에서 GPU 점수와 모두 일치했다.
기존 데이터·모델·소스 보호 해시를 최종 재확인했다. 앱 테스트 196개와 학습 도구 테스트 59개가 통과했다.
모델과 체크포인트·토크나이저·manifest는 실행 02의 `safety/`에, 전체 비교는 `comparison.json`에 있다.
새 C# 전달 ZIP은 만들지 않았다. 기존 C# 라이브러리는 새 출력 이름·크기와 관련도 3점 통과 조건을 적용해야 한다.
