# Filtering AI Labeling Guideline

## 1. 목적

ALTONG 필터링 AI는 현재 작업 맥락(`CurrentContext`)과 수신 알림(`RawNotification`)을 함께 분석하여
알림의 긴급도와 현재 작업과의 연관도를 판단한다.

모델은 다음 값을 출력한다.

- `urgency_score`: 알림 자체의 긴급도
- `relevance_score`: 현재 작업과의 연관도
- `category`: 알림 카테고리
- `ai_summary_reason`: 판단 이유

최종 `is_passed` 값은 모델이 직접 결정하지 않고,
`urgency_score`와 `relevance_score`를 기반으로 별도의 정책 로직에서 계산한다.

이 구조를 통해 모델 학습과 실제 알림 필터 정책을 분리하고,
향후 사용자별 집중 강도나 선호도에 따라 정책만 수정할 수 있도록 한다.

---

## 2. 입력 데이터

필터링 AI의 입력은 클라이언트의 Data Contract를 그대로 사용한다.

### RawNotification

- `id`
- `app_name`
- `sender`
- `title`
- `body`
- `timestamp`

예시:

{
  "id": "noti_20260913_001",
  "app_name": "Slack",
  "sender": "김철수 팀장",
  "title": "[긴급] 서버 배포 오류",
  "body": "지금 서버 에러가 발생해 긴급 핫픽스 부탁드립니다.",
  "timestamp": "2026-09-13T18:05:00Z"
}

### CurrentContext

- `active_process`: 현재 활성 프로세스 이름
- `window_title`: 현재 활성 창 제목
- `last_updated`: 맥락 캡처 시각
- `duration_seconds`: 현재 창에 머문 시간(초). 기본값은 0
- `recent_processes`: 최근 1~2분 동안 교차 사용한 프로세스 이름, 최신순 최대 3개

예시 (모델 입력에서는 snake_case로 통일):

{
  "active_process": "Code.exe",
  "window_title": "auth_controller.py - ALTONG - Visual Studio Code",
  "last_updated": "2026-09-13T18:04:55Z",
  "duration_seconds": 45,
  "recent_processes": ["Code.exe", "chrome.exe", "WindowsTerminal.exe"]
}

이전 샘플처럼 새 필드가 없거나 `recent_processes`가 `null`이면 모델
입력에서는 각각 0과 빈 목록으로 정규화한다. 클라이언트의 `Empty`는
프로세스·창 제목이 빈 문자열이고 경과 시간은 0이다. 이때
`last_updated`만으로 현재 작업을 추측하지 않는다.

최근 프로세스는 작업 세트의 단서일 뿐 작업 제목이나 중요도 자체를
알려주지 않는다. `urgency_score`는 알림 자체로 판단하고,
`relevance_score`를 정할 때 현재 창 정보와 함께 제한적으로 참고한다.

모델은 위 정보만을 이용하여 판단한다.

`timestamp`와 `last_updated`는 UTC 기준 ISO 8601 형식을 사용하며,
문자열 끝에 `Z`를 붙인다.

입력에 존재하지 않는 사용자 개인 일정, 실제 인간관계의 중요도,
이전 대화 내용 등의 정보는 추측하지 않는 것을 원칙으로 한다.

## 3. urgency_score

`urgency_score`는 알림을 얼마나 빨리 확인해야 하며,
놓쳤을 때 얼마나 큰 문제가 발생할 수 있는지를 종합하여 판단한다.

| 점수 | 기준 |
|---|---|
| 1 | 언제 확인해도 거의 문제가 없음 |
| 2 | 나중에 확인해도 큰 문제가 없음 |
| 3 | 비교적 빠른 확인이 필요하지만 즉시는 아님 |
| 4 | 현재 작업을 잠시 중단하고 확인할 가치가 있음 |
| 5 | 즉시 확인 또는 대응이 필요한 수준 |

### 판단 시 참고 요소

긴급도를 라벨링할 때 다음 요소를 내부 기준으로 참고한다.

#### 시간 민감도

- 언제 확인해도 되는가
- 오늘 안에 보면 되는가
- 수십 분 내 확인해야 하는가
- 즉시 확인해야 하는가

#### 영향도

- 놓쳤을 때 영향이 거의 없는가
- 작은 불편만 발생하는가
- 업무나 일정에 영향을 주는가
- 금전적, 보안적, 업무적 또는 개인적으로 큰 피해가 발생할 수 있는가

#### 행동 필요성

- 단순 정보 전달인가
- 확인만 하면 되는가
- 응답, 수정, 승인, 전화 등의 실제 행동이 필요한가

위 세 요소는 모델의 최종 출력 필드가 아니라
사람이 `urgency_score`를 일관되게 라벨링하기 위한 판단 기준으로 사용한다.

### 예시

"오늘 치킨 3,000원 할인"

- 시간 민감도: 낮음
- 영향도: 매우 낮음
- urgency_score = 1

"보유 쿠폰이 10분 후 만료됩니다"

- 시간 민감도: 높음
- 영향도: 낮음
- urgency_score = 2

"오늘 중 코드 리뷰를 부탁드립니다. 즉각적인 운영 영향은 없습니다"

- 시간 민감도: 오늘 안에 확인하면 됨
- 영향도: 즉시 놓쳐도 큰 문제가 명시되지 않음
- urgency_score = 3

`오늘 중`이라는 기한만으로 현재 작업을 중단할 수준인 4점을 부여하지 않는다.
즉시 확인하지 않을 때 발생하는 구체적인 영향이 있으면 그 근거를 함께 판단한다.

"오늘 제출해야 하는 과제 파일이 누락되었습니다"

- 시간 민감도: 높음
- 영향도: 높음
- urgency_score = 4

"운영 서버 로그인 장애 발생, 즉시 확인 필요"

- 시간 민감도: 매우 높음
- 영향도: 매우 높음
- urgency_score = 5

"가족이 응급실로 이동 중이니 전화해"

- 시간 민감도: 매우 높음
- 영향도: 매우 높음
- urgency_score = 5

## 4. relevance_score

`relevance_score`는 수신된 알림이
사용자가 현재 수행 중인 작업과 얼마나 직접적으로 연결되어 있는지를 평가한다.

판단 시 `active_process`와 `window_title`을 주요 맥락 정보로 사용한다.

| 점수 | 기준 |
|---|---|
| 1 | 현재 작업과 완전히 무관 |
| 2 | 같은 조직 또는 분야이지만 현재 작업과 거의 무관 |
| 3 | 같은 분야나 주제지만 현재 작업에 주는 도움은 불분명 |
| 4 | 현재 목적에 직접 도움이 되는 정보나 요청 |
| 5 | 현재 작업의 정확한 대상이나 행동과 연결됨 |

### 예시

현재 작업:

`auth_controller.py - Visual Studio Code`

알림별 예시:

- 게임 할인 알림 → 1
- 회사 회식 장소 투표 → 2
- 같은 프로젝트 README 수정 → 3
- 같은 프로젝트지만 현재 작업과 관계가 불분명한 PR 리뷰 요청 → 3
- 현재 인증 기능 개선에 도움이 되는 PR 리뷰 요청 → 4
- auth API 스키마 변경 → 5

관련도는 앱 이름이나 발신자만으로 결정하지 않는다.
같은 분야나 주제라는 이유만으로 4점 이상을 부여하지 않는다.
예를 들어 운동화를 비교하는 중에 받은 운동화 할인 안내는 구매 목적에
도움이 되므로 4점이고, 정확히 비교 중인 제품의 가격 인하는 5점이다.
공부 중에 받은 공부 관련 농담은 현재 공부에 주는 도움이 불분명하므로
3점 이하로 판단한다. 통과시키기 위해 긴급도나 관련도 점수를 높이지 않는다.

---

## 5. category

카테고리는 자유 생성하지 않고
다음 값 중 하나를 사용한다.

- 긴급 업무
- 일반 업무
- 일정/회의
- 시스템/보안
- 개인 중요
- 개인 일반
- 광고/홍보
- 기타

카테고리는 알림의 성격을 설명하기 위한 보조 정보이며,
PASS/BLOCK을 직접 결정하는 기준으로 사용하지 않는다.

---

## 6. ai_summary_reason

`ai_summary_reason`은 모델이
왜 해당 긴급도와 연관도를 부여했는지 한 문장으로 설명한다.

예시:

"현재 작업 중인 인증 API에서 장애가 발생하여 즉시 확인이 필요함"

"현재 프로젝트와 관련된 메시지지만 즉시 확인할 필요는 없음"

"현재 작업과 무관한 일반 광고 알림임"

판단 이유는 짧고 명확하게 작성하며,
입력 데이터에서 확인할 수 없는 내용을 추측하지 않는다.

---

## 7. PASS/BLOCK 정책

최종 `is_passed` 값은 모델이 직접 생성하지 않는다.

모델이 출력한 `urgency_score`와 `relevance_score`를 기반으로
별도의 정책 로직에서 결정한다.

긴급한 알림 또는 현재 목적에 직접 도움이 되는 알림을 통과시킨다.
정책 버전은 `urgency4_or_relevance4_v2`이며, 이전 정책으로 계산한
실험 결과와 정책 정확도·오차단·오통과 수치를 직접 비교하지 않는다.

### 기본 규칙

- `urgency_score >= 4` → PASS
- `relevance_score >= 4` → PASS (긴급도와 관계없이 적용)
- 그 외 → BLOCK

이 규칙은 **집중 모드가 켜져 필터링이 수행되는 동안** 적용한다.
`active_process`와 `window_title`이 비어 있어도 집중 모드가 종료되거나
사용자가 쉬고 있다고 추정하지 않는다. 현재 작업을 알 수 없으면
`relevance_score`를 높게 추측하지 않고 같은 PASS/BLOCK 규칙을 적용한다.
집중 모드의 시작·종료는 창 정보가 아닌 세션 상태로 판단한다.

예시 코드:

if urgency_score >= 4:
    is_passed = True
elif relevance_score >= 4:
    is_passed = True
else:
    is_passed = False

BLOCK은 알림을 삭제한다는 의미가 아니다.

BLOCK된 알림은 즉시 팝업으로 표시하지 않고,
로컬 DB에 저장하여 집중 세션 종료 후 확인할 수 있도록 한다.

## 8. 라벨링 원칙

### 8.1 발신자만 보고 판단하지 않는다

잘못된 예:

- 팀장 → 무조건 높은 긴급도
- 친구 → 무조건 낮은 긴급도

올바른 예:

"다음 달 회의실 예약 부탁해요"
- 발신자: 팀장
- urgency_score: 낮음

"교수님이 발표 시간을 5분에서 3분으로 바꿨대"
- 발신자: 친구
- urgency_score: 높을 수 있음

발신자는 의미 판단을 위한 맥락 정보일 뿐,
점수를 직접 결정하는 규칙이 아니다.

### 8.2 앱 이름만 보고 판단하지 않는다

예:

Slack 광고
→ 낮은 긴급도

Slack 서버 장애
→ 높은 긴급도

KakaoTalk 잡담
→ 낮은 긴급도

KakaoTalk 가족 응급 상황
→ 높은 긴급도

### 8.3 긴급도와 연관도를 독립적으로 판단한다

예:

현재 작업:
ALTONG 코드 작성

알림:
"가족이 응급실로 이동 중이니 전화해"

- urgency_score = 5
- relevance_score = 1
- PASS

현재 작업:
ALTONG 코드 작성

알림:
"README 오타 수정했습니다. 시간 될 때 확인해주세요"

- urgency_score = 1~2
- relevance_score = 3 (현재 수정 중인 코드에 주는 도움이 불분명한 문서 오타 수정)
- BLOCK

현재 작업과 관련이 없어도 매우 긴급한 알림은 통과하며,
긴급도가 낮아도 현재 목적에 직접 도움이 되는 알림은 통과한다.

### 8.4 현재 입력으로 판단할 수 없는 정보는 추측하지 않는다

예:

"전화 좀 해"

이 메시지만으로는
단순 통화 요청인지 응급 상황인지 명확하지 않을 수 있다.

이 경우 모델은 입력에 존재하지 않는 상황을 임의로 만들어내지 않는다.

이러한 모호한 사례는 별도 경계 사례 데이터로 관리하고,
향후 사용자 피드백 또는 추가 맥락 데이터가 확보되면 개선한다.

---

## 9. 모델 출력 구조

모델의 학습 목표 출력은 다음 형태를 사용한다.

{
  "urgency_score": 5,
  "relevance_score": 4,
  "category": "긴급 업무",
  "ai_summary_reason": "현재 작업과 관련된 서버 장애로 빠른 확인과 대응이 필요함"
}

`notification_id`는 모델이 생성하지 않는다.

입력으로 전달된 `RawNotification.id`를
정책 및 후처리 단계에서 그대로 사용한다.

`is_passed` 역시 모델이 직접 생성하지 않고,
정책 엔진에서 계산한다.

---

## 10. 최종 FilterResult 생성

정책 엔진에서는 모델 출력과 원본 알림 ID를 조합하여
최종 `FilterResult`를 생성한다.

예시:

{
  "notification_id": "noti_20260913_001",
  "is_passed": true,
  "urgency_score": 5,
  "relevance_score": 4,
  "category": "긴급 업무",
  "ai_summary_reason": "현재 작업과 관련된 서버 장애로 빠른 확인과 대응이 필요함"
}

이 형식은 클라이언트와 합의된 기존 Data Contract를 유지한다.

---

## 11. 데이터셋 라벨링 순서

각 데이터 샘플은 다음 순서로 라벨링한다.

1. `RawNotification`의 앱, 발신자, 제목, 본문, 시간을 확인한다.
2. `CurrentContext`의 프로세스와 윈도우 제목을 확인한다.
3. 시간 민감도를 생각한다.
4. 놓쳤을 때 발생할 영향도를 생각한다.
5. 사용자의 행동 필요성을 확인한다.
6. 위 요소를 종합하여 `urgency_score`를 1~5로 결정한다.
7. 현재 작업과 알림의 의미적 관계를 판단하여 `relevance_score`를 1~5로 결정한다.
8. 정의된 카테고리 중 하나를 선택한다.
9. 한 문장의 `ai_summary_reason`을 작성한다.
10. 정책 로직을 적용하여 최종 PASS/BLOCK 값을 계산한다.

## 12. 경계 사례

다음과 같은 사례는 데이터셋에 의도적으로 포함한다.

- "전화 좀 해"
- "잠깐 확인해줘"
- "급한 건 아닌데 연락 가능?"
- 현재 프로젝트와 관련 있지만 마감이 없는 메시지
- 시간이 임박했지만 영향이 작은 쿠폰/이벤트 알림
- 현재 업무와 무관하지만 보안 또는 금전적으로 중요한 알림
- 현재 작업 중인 코드에 직접 영향을 주는 API 변경
- 현재 작업과 같은 프로젝트지만 나중에 확인해도 되는 PR/문서 변경
- 빌드 완료, 학습 완료, 다운로드 완료 등의 작업 완료 알림

이러한 데이터는 단순한 명확 사례보다
모델의 실제 필터링 성능을 검증하는 데 중요하다.

---

## 13. 평가 원칙

`urgency_score`와 `relevance_score`는 1~5의 순서형 점수이므로
정확히 같은 점수를 맞췄는지만 평가하지 않는다.

다음 지표를 함께 확인한다.

- Exact Accuracy
- ±1 Accuracy
- MAE
- Macro F1
- PASS/BLOCK Accuracy
- 긴급 알림 오차단 비율
- 불필요 알림 오통과 비율
- JSON 형식 준수율

특히 실제 서비스에서는
긴급 알림을 잘못 BLOCK하는 경우를 중요하게 평가한다.

---

## 14. 기본 설계 원칙

ALTONG 필터링 AI의 목표는
모든 알림의 중요도를 완벽하게 이해하는 것이 아니다.

핵심 목표는 다음과 같다.

- 명확하게 긴급한 알림은 놓치지 않는다.
- 현재 작업에 직접 영향을 주는 알림은 필요한 경우 통과시킨다.
- 현재 목적에 직접 도움이 되는 알림은 긴급도가 낮아도 통과시킨다.
- 앱 이름이나 발신자만으로 중요도를 판단하지 않는다.
- 입력에 존재하지 않는 정보를 임의로 추측하지 않는다.
- AI 모델의 의미 판단과 최종 필터 정책을 분리한다.
- 기존 클라이언트 Data Contract를 유지한다.
- 향후 사용자 피드백에 따라 정책을 수정할 수 있도록 설계한다.

## 15. 학습용 알림 문구 작성 원칙

학습용 `title`과 `body`에는 사용자가 화면에서 실제로 볼 법한
알림 내용을 쓴다. "메시지가 도착했습니다", "관련 내용을 확인할 수
있습니다"처럼 알림을 제3자가 설명하는 문장은 원문 메시지 대신 넣지 않는다.

메신저 알림은 발신자를 `sender`에 기록하고, `title`은 표시되는
발신자 또는 대화방 이름, `body`는 발신자가 보낸 짧은 문장으로 쓴다.
친구·가족·동료·고객·채널의 말투를 상황에 맞게 다르게 작성한다.
문장 부호, 축약어, 이모티콘, 영어 혼용은 실제 사용 범위에서 허용한다.

같은 앱 안에 업무 연락, 가족의 긴급 연락, 친구의 농담, 광고 등 여러
카테고리와 긴급도를 섞는다. 앱 이름이나 말투만으로 정답을 알 수
있게 만들지 않는다. 한 창에도 관련 알림과 무관한 알림이 모두
등장하도록 문맥을 구성한다.

표현만 바꿀 때는 시간, 영향, 행동 요청, 주제의 의미가 바뀌지 않았는지
확인한다. 의미가 바뀌면 기존 점수를 그대로 재사용하지 않고 다시
라벨링한다. 합성 예시는 가상의 인물과 상황으로 작성한다.
